# Trellium 项目记忆与历史留痕边界复评

- 日期：2026-09-30
- 基线：远端 `develop`，commit `a01950a1afab092ae4296b29a00c1b9da74fd7ab`。
- 核实方式：执行 `git ls-remote https://github.com/zlin101/trellium.git refs/heads/develop`，其结果与本地 HEAD 一致。
- 需求上下文：[本轮定位讨论](2026-09-30-trellium-positioning.md)与 owner 本次给出的三层模型建议。定位讨论文件当前为本地新增资料；未把它描述为远端已提交内容。
- 评审范围：目标、信息职责、已有协议和必要的最小调整。收到的建议到第三部分标题为止，未推断未提供的后续内容。
- 交付性质：设计复评与建议，现行协议、Decision 状态和存储行为均保持原状。

## 1. 冻结本轮评审的目标

本轮按 owner 当前指令使用以下目标：

> Trellium 是面向个人长期开发的、可迁移的 Agent 协作与项目上下文协议。

它应支持换 session、Agent、CLI 后继续项目，并减少 owner 重复解释工作方式的成本。接手者应能理解当前设计的原因、feature 进度、完成依据、遗留缺陷、下一步，以及值得重新评估的判断。开发流程负责持续维护这些上下文。

材料范围为 Trellium 已管理的 TASK、review ledger、长期 decision/rationale、被替代的结构化上下文及必要执行依据。不要求完整聊天、tool trace、terminal output 或思考过程的采集。

历史 Decision 提供当时的问题、约束和推理证据。`Active` 不能代替对当前方案正确性的论证。重新推理可以挑战旧方案；执行涉及治理、持久数据或其他风险域的变更，仍需明确当前任务的授权边界。

## 2. 评审结论

建议采用 Operational State、Canonical Knowledge、Historical Evidence 三类职责作为记忆模型的主分类。

现有仓库已经包含部分历史证据机制：执行记录、Decision 背景与依据、带时间戳的历史快照、里程碑归档。准确的缺口是：**历史证据尚未获得贯穿关闭、归档、查找与恢复的持久性契约。**

因此，本轮的设计方向是把已有材料的职责与转换规则讲清，补上持久可找回的边界；没有证据表明必须先引入 DB、服务或复杂 Agent runtime。

## 3. 从目标推导三类职责

| 信息职责 | 需要回答的问题 | 读取与维护要求 |
| --- | --- | --- |
| Operational State | 当前可以继续做什么，执行现场是什么？ | 从当前 TASK、工作区与测试等事实源确认；允许频繁更新；可行动事实仍需唯一 owner。 |
| Canonical Knowledge | 当前实现与协作应依据什么事实、约束和判断？ | 按任务路由读取；当前有效正文有明确 owner；可以在新证据下修订。 |
| Historical Evidence | 当时发生过什么，当前结论从何而来？ | 持久、可检索、默认不读；保留历史版本与出处；不授予 Authority，不充当当前状态。 |

三类职责回答不同的问题。摘要会筛选和压缩原始材料，不能保证以后能从摘要重建原始证据；历史保存也不能替代对当前事实的更新。

读取频率、Git 策略、物理位置和持久性是其他维度：

- 当前事实可以按需读取，仍然属于 Canonical Knowledge。
- Operational State 可以必须持久，例如需要跨 session 继续的活跃 TASK。
- local 材料可以私有且持久；忽略 Git 并不必然意味着可以丢失。
- 历史可在 repo 内或外保存；具体位置不能代替持久可恢复的验证。

### 分类应落到内容职责，避免机械按文件分类

- active TASK 的当前契约、slice 和 gate 属于 Operational State；已经发生的 Execution Record 属于 Historical Evidence。
- 未收敛 review ledger 中的待处理 findings 属于 Operational State；历轮审查与修复依据具有历史职责。
- 当前认可的 rationale 属于 Canonical Knowledge；旧前提、旧推理与被替代版本属于 Historical Evidence。
- 今天重跑的测试描述当前状态；某个 commit 上的旧测试结果只能证明当时的执行情况。

上述内容可以共存于现有文件中。三类职责不自动要求三个新目录、三套 schema 或独立服务。

## 4. 仓库事实与具体问题

### 4.1 已有基础：唯一 owner 与历史快照已经存在

[10-vault](../../init/protocol/10-vault.md)已规定同一事实只有一个权威位置，其他位置可以是派生投影或带时间戳的历史快照；当前 TASK 契约与 Execution Record 的职责也已区分。

因此，“历史证据完全缺失”不准确。可复用这条基础，把当前事实唯一性与历史可追溯性同时表达清楚。

### 4.2 D-0006 的推理需要重做

[D-0006](../../vault/decisions/D-0006-local-task-boundary.md)将 local TASK 定义为私有、临时、可丢弃的日志，并因“制造第二事实源”否决过自动发布/归档。

其当时解决的问题仍有价值：降低仓库负担、避免摘要授予恢复权限、关闭前蒸馏长期事实。但下面两条推导不充分：

1. 私有和低仓库负担，并不推出允许丢失历史材料。
2. 保留带明确时间与来源的历史版本，并不必然建立第二个当前事实 owner。

本轮 owner 已明确要求外移后持久可找回，因此“可丢弃”承诺无法直接沿用。D-0006 应作为待复评的旧解决方案，保留原问题与理由；本次尚未修改其状态。

[D-0012](../../vault/decisions/D-0012-local-default-task-storage.md)所针对的“过程日志不默认进入业务仓库”仍与新目标兼容。默认 local 是否合适，与 local 材料是否必须持久是两个问题，不必一起推翻。

### 4.3 Canonical 蒸馏与历史保全必须分别判断

现有 [10-vault](../../init/protocol/10-vault.md)和[治理协议](../../init/protocol/20-governance.md)要求 local lifecycle 关闭前完成 Durable Knowledge Disposition：`none` 或 `distilled`。

这个 gate 回答了有没有新长期事实、它的正式正文在哪里，但没有单独回答任务契约、审查过程与必要执行依据保存在哪里。

一项任务可以没有新长期约束，但仍有值得保全的验收与审查证据。反过来，TASK 全文保全了，也不代表当前项目知识已经更新。

### 4.4 现有归档主要解决 repo 内重组

[15-vault-compaction](../../init/protocol/15-vault-compaction.md)定义把已关闭 TASK 纯移动到 `vault/tasks/archive/`，也定义归档区只增和结构性压缩。

这已经提供了“退出当前读取路径”的基础，但不等于完成 repo 外持久保存。在 local 模式下，`archive/` 也被忽略 Git；fresh clone 不带这些内容符合现行 storage contract，却不能据此宣称历史已被另一份持久副本覆盖。

### 4.5 review ledger 的保留粒度存在真实取舍

[80-execution-patterns](../../init/protocol/80-execution-patterns.md)规定收敛后将台账结论并入 TASK Execution Record，不再单独保留；收敛前中间状态被视为瞬态工作材料。

新目标明确包含 review ledger，需要决定保存的历史证据粒度。建议至少保留已有的历轮 findings、处置、理由、复核与必要证据引用；复制 ledger 的最终版本是否足够，取决于它是否已经保留这些轮次。

目前用户尚未要求捕获每次编辑或文件写入。不应把这一差距扩张成完整会话录制需求，也不应未经讨论就将所有中间轮次压缩成最终一句结论。

### 4.6 闭合 TASK 后，feature 仍有当前事实

“TASK 当时 accepted”只能证明某次任务的验收事件。此后 feature 可能有回归、新缺陷或新的取舍。TASK 进入历史后，新 Agent 仍需找到该 feature 当前的范围、完成依据、已知问题与后续事项。

建议先利用现有项目文档、API/架构文档、Decision 和索引承载这些事实及证据链接。是否有必要新增 feature 状态载体，要由具体接续失败案例证明。

## 5. 建议补齐的最小契约

以下为后续方案应具备的语义要求，未实施为现行 gate 或 schema。

1. **当前事实的维护位置。** 关闭任务时，确认实现结论、遗留问题和需要未来遵循的判断已在明确的当前 owner 中；TASK 不承担永久的 feature 当前状态。
2. **历史证据的独立保全。** 对已纳入范围的 TASK、review 和替代版本，记录其历史去向与检索入口。即使没有新 Canonical Knowledge，仍应独立判断历史保存是否完成。
3. **外移可验证。** 至少能说明来源、目标、所属项目与记录身份、版本或时间、引用关系，以及核对和恢复结果。具体格式尚未决定。
4. **先保全、后清理。** 目标内容完整且可读取、引用已更新之后，才移除源副本；失败时源记录保留。不得把源删除成功当作归档成功。
5. **历史检索不激活任务。** 历史里原有的 lifecycle、Authority 数字或执行指令仅解释当时。重新开展工作时应建立当前契约。
6. **修正保留前后证据。** 修改当前判断时保留旧版来源和替代关系；历史错误可通过新增更正说明解释，避免覆写成“当时就知道”。

上述契约可先由 Markdown、文件目录及清楚的操作流程表达。是否需要机器校验，再依据实际遗漏和失效案例决定。

### 尚未确定的边界

- 持久可找回需覆盖哪些场景：切换 CLI、删除工作副本、fresh clone、换设备、存储损坏？应明确哪些由协议保证、哪些由 owner 的存储与备份措施保证。
- review 的历轮证据保留到什么粒度，现有台账内容是否足够？
- 采用 repo 内保留、repo 外归档或两者配合；如何保证不同保存方式都有清楚的查找入口？
- 旧资料的保全策略：当前尚存材料如何处理；已经消失的历史只能报告缺口，不能伪造恢复。

`/tmp` 在本轮定位讨论中只是候选。它不能在没有持久与恢复保障的情况下，独自承担本轮承诺。数据库同样需要回答保存、备份与引用问题，仅换容器无法解决职责边界。

## 6. 用场景验证设计，而非只核对术语

建议后续至少验证：

| 场景 | 需要观察的结果 |
| --- | --- |
| 新 Agent 正常接手 | 能按入口找到当前设计原因、进度、依据、缺陷和下一步；默认无需展开全部历史。 |
| 无新长期结论的 TASK 关闭 | Canonical disposition 可为 `none`，但其结构化历史仍按选定契约可找回。 |
| 旧 rationale 被替代 | 当前读取指向新判断；需要追溯时能找到旧前提、理由及替代关系。 |
| 外移中途失败 | 源记录仍可用；报告失败，不能声称历史保全完成。 |
| 查阅历史 TASK | 能核对当时依据，不会把旧 Authority 或 slice 当作当前授权与行动。 |
| 删除当前工作副本后恢复 | 若选定契约承诺该场景，能通过约定入口取回历史，且不会混淆当前状态。 |

这些是待执行的行为验证，本轮只做协议文本复评，没有宣称通过。

## 7. 两轮反思与后续范围

第一轮从已冻结目标检查覆盖：当前 owner、长期蒸馏、历史材料已有基础；D-0006、关闭 gate、review 保留粒度和外移契约存在具体缺口。

第二轮检查最小性：职责划分不要求目录重构；local 仍可保留低仓库负担的价值；handoff 的纯 transient delta 不因本轮而自动进入永久历史。数据库、服务、完整会话采集和自动语义提取都没有被当前证据证明为必需。

推荐先写清三类职责与关闭/替代/外移的转换规则，再用一项真实 feature 做接续与追溯验证。验证指出必要机制后，另立限定范围的实施契约。

本次形成的是复评建议；没有更改 Active Decision、现行协议或资料存储位置。
