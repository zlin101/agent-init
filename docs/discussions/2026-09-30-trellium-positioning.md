# Trellium 定位讨论：个人开发习惯、项目上下文与留痕

- 日期：2026-09-30
- 参与方：项目 owner、Codex
- 用途：保留本轮追问的过程与结果，供后续与 GPT、Codex 继续收敛定位和优化细节。

本文是讨论记录。逐题确认的需求、助手提出的定位措辞、仓库现状和待讨论问题分别标明；本文不修改现行协议、授权、存储契约或已有 Decision 的状态。

## 1. 起点：究竟想把这个 repo 做成什么？

用户原始问题：

> 我究竟想将 trellium 这个 repo 做成什么？个人习惯的可迁移“藤蔓”？一个留痕的开发技能？个人习惯的留痕？

助手先将这几个提法拆开：个人习惯是要承载的内容，可迁移是能力，留痕是机制，Skill 是交付形式。它们可以共存，需要进一步确定主要痛点和成功标准。

## 2. 追问过程与用户回答

### 第一轮：主要痛点与服务对象

**Q1：如果 trellium 消失，最不能接受什么损失？**

追问给出四类损失：

- A：换项目或 Agent，要重新解释个人习惯、标准和禁忌。
- B：换会话后，要重新解释项目决策、当前进度和有效结论。
- C：Agent 跳过认可的开发步骤，需要反复盯范围、验证和验收。
- D：事后说不清做过什么、为什么算完成、谁确认过。

助手最初建议将 C 作为首要假设；用户的回答修正了这个判断：**ABCD 都有，B 尤甚，A 也突出。**

用户给出的 A 类例子：切换 Agent CLI 后，仍需重新说明要读哪个文件、读完做什么，以及自己的开发流程。

用户给出的 B 类例子：开发后期，如果此前没有按流程记录，Agent 必须重新读代码、理解设计，甚至无法知道：

- 当时做了什么决定，为什么做这个决定；
- 这个决定会带来什么后果；
- 某个 feature 是否完成、做到哪里；
- 还有什么缺陷。

用户强调，这需要负责的 repo 上下文管理和记录，不能依赖模型记住，也不能仅靠零散、简单的文档解决。

**Q2：当个人习惯与其他开发者的习惯冲突，谁决定默认值？**

用户选择 A：**首先符合自己的习惯，别人可以借用、修改。** 当前用户只有 owner 本人；如果以后受到欢迎，再考虑扩展能力，本阶段不围绕其他用户设计。

这一轮明确：项目长期上下文的接续是主要痛点，个人开发习惯决定维护这些上下文的方式；通用产品化尚非当前目标。

### 第二轮：接续标准、保留内容与维护成本

**Q3：新 Agent 接续到什么程度才算成功？**

用户确认以下标准：新 Agent 能从记录中理解设计原因与取舍、完成进度及依据、遗留缺陷和未解决问题、下一步与需要重新评估的决定，然后有针对性地查代码核对。

本阶段不要求完整恢复当时的所有探索、失败尝试和讨论。目标是避免每次都先重新考古，才能开始工作。

**Q4：结论与依据完整保留后，过程记录能否退出？**

用户同意有效结论及其依据必须保留，但明确修正了“丢弃”的含义：**退出当前 repo 应理解为移出，而非删除。**

用户临时提出的载体包括指定的 `/tmp/***file***` 路径或 DB 文件，并表示都可以考虑。这是候选思路，尚未选择具体路径、数据库或实现。

**Q5：愿意为可信上下文付出什么日常成本？**

用户选择 B：**把上下文更新和验收依据作为完成条件，由自己检查关键结论。** 功能能跑并不自动代表开发完成。

### 第三轮：归档承诺与迁移边界

**Q6：有效结论完整，但外移的过程记录被清理，能否接受？**

用户选择 B，不能接受；并补充“移出操作最好可以写清楚”。过程可以离开当前 repo，但需要持久保存并可找回。

因此，仅写入一个临时路径不足以证明满足本轮要求。后续需决定如何保障持久性、记录去向和恢复入口。

**Q7：要保留哪些过程？**

用户选择 A：当前范围是 trellium 管理的任务记录、审查记录、被替代的上下文等结构化过程材料。本阶段不扩展到采集完整 Agent 对话、工具调用和终端输出。

**Q8：可迁移跨越哪些边界？**

用户同意本阶段承诺两项：

1. 同一项目切换 Agent：新 Agent 能找到入口、遵循流程、接续项目事实。
2. 开始另一个项目：带过去的是个人开发规则与偏好；各项目分别维护自己的决策与进度。

本阶段不要求新项目主动检索其他项目的历史经验。

### 最后一轮反馈：已有能力与优化方向

助手提出一份定位汇总后，用户要求将过程和结果输出为文档，以便后续继续与 GPT、Codex 讨论，并指出：

> 其实我们很多都已经做了，就是细节还需要优化一下子。

因此，后续应先核对已有能力、识别具体差距，再决定最小优化。逐题需求已经得到明确回答；汇总定位的措辞仍可继续打磨，没有因此自动形成新的正式架构决策或实施授权。

## 3. 当前工作定位

以下是助手根据已确认回答提出的定位草案：

> Trellium 是从我的个人开发习惯孵化的、可迁移的 Agent 协作与项目上下文管理协议，让项目在长期开发和切换 Agent 后，仍能被可信地接续。

三个原始提法的关系：

| 提法 | 在定位中的作用 |
| --- | --- |
| 个人开发习惯 | 定义如何开发、验证、维护上下文，以及什么才算完成。 |
| 可迁移的“藤蔓” | 将工作方式带进不同项目，让不同 Agent 能找到入口并接续工作。 |
| 留痕 | 保留决策、取舍、完成依据和遗留问题，为未来行动提供依据。 |
| Skill | 已有的协议交付与操作载体。 |

上下文的可靠性包含两方面：记录足以支撑接续；开发流程会持续更新、核对这些记录。助手据此将“简单文档不够”理解为：还需要明确关联、职责、有效性与维护流程。具体关联怎样表达，仍需后续验证。

## 4. 已确认的需求与阶段边界

- 主要价值是项目上下文长期接续，同时减少切换 Agent 时重复解释个人工作方式的成本。
- 首先服务 owner 的真实开发习惯；多用户扩展不属于当前阶段。
- 当前项目必须保留有效结论及其依据，让接手者理解原因、进度、缺陷和下一步。
- 上下文更新与验收依据属于完成条件，owner 检查关键结论。
- 退出当前 repo 的结构化过程记录应持久外存、可找回，并写清移出操作。
- 当前不要求完整开发会话采集，也不要求跨项目经验检索。
- 文件归档与 DB 都仍是候选；本轮未决定具体实现，也未要求立即迁移任何记录。

### 必须单独复评的差异：local TASK 的“可丢弃”

当前 [D-0006](../../vault/decisions/D-0006-local-task-boundary.md)仍为 Active，定义 local TASK 是私有、临时、可丢弃的工作日志；长期约束蒸馏进 canonical 文件，且此前否决过自动发布/归档 local TASK，以避免第二事实源。[collaboration](../../vault/collaboration.md)也保留了对应偏好。

本轮用户提出了更强的要求：结构化过程材料移出当前 repo 后也必须持久可找回。这与旧的“可丢弃”边界存在张力，不能通过换一个目录名称就宣称满足，也不能把“repo 内已有 archive”视为已经实现外存保障。

后续应先明确新要求适用的材料和场景，再决定是否及如何复评 D-0006。本文保留这项差异，未改写旧 Decision 或实施外移。

## 6. 后续与 GPT、Codex 继续讨论的问题

以下是助手建议的讨论清单，不是本轮已经选择的实现方案。

1. **先定位真实摩擦。** 哪次切换 CLI 或接续旧 feature 仍需 owner 补充上下文？问题来自入口未发现、记录遗漏、关联不清、内容过期，还是执行不遵从？
2. **明确有效结论的最小内容。** 哪些决策、取舍、完成依据和缺陷必须保留？现有文件是否已经足够，哪里只需改善内容或路由？
3. **明确外存归档契约。** 移出对象、触发时机、来源与目的地、检索入口、持久性验证、恢复办法、失败处理分别是什么？如何保证操作没有丢失内容？
4. **划清摘要与归档的职责。** 项目内有效结论如何指向外部过程依据？归档是否只保存历史，避免成为与当前状态竞争的第二事实源？
5. **复评 local 的可丢弃边界。** 新要求覆盖所有结构化过程记录，还是其中部分？保持低仓库负担与持久可找回，如何同时满足？
6. **验证接续效果。** 让未参与任务的 Agent 回答设计原因、进度与依据、遗留缺陷、下一步，并核对回答的出处。具体场景、成本和通过标准待定。

推荐讨论顺序：具体摩擦 → 已有机制 → 最小优化 → 验证 → 确有必要时再调整契约或存储。文件与 DB 的选择放在需求和差距明确之后。
